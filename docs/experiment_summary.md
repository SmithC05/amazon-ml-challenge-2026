# Experiment Summary

## Objective
Train a baseline Business Entity Resolution matching model (Member 3 task) that takes candidate pairs from the blocking stage and classifies them as match (1) or non-match (0), maximizing the entity-level F0.5 score.

## Baseline Setup & Data
- **Training Data:** 945,996 total pairs (positive and negative) derived from the ground truth. Same-country negative sampling was used, avoiding Cartesian product explosion.
- **Train/Validation Split:** 80/20 split based strictly on unique `s1_entity_id` to prevent data leakage (80,000 S1 entities for train, 20,000 for validation).

## Feature Set
Extracted via `src/features.py` (after standardizing via NFC, lowercasing, and whitespace collapse):
1. **Name Features:** Exact match, Jaccard, token overlap, Levenshtein ratio, length difference, token count difference.
2. **Address Features:** Exact match, Jaccard, token overlap, Levenshtein ratio, length difference, token count difference, missingness flag.
3. **Other:** Country match, source indicators (`source_is_s2`, `source_is_s3`).

## Baseline Model
- **Pipeline:** `StandardScaler` + `LogisticRegression(max_iter=1000, random_state=42)`

## Evaluation & Threshold Sweep
Evaluation is based on macro-averaged F0.5 per S1 entity. A threshold sweep from 0.50 to 0.95 determined the optimal cutoff.

**Final Stored Metrics:**
- **Threshold:** 0.75
- **Precision:** 0.998541
- **Recall:** 0.992368
- **F0.5:** 0.997300

## Error Analysis Observations
- **False Positives (101):** Often triggered by partial address overlaps combined with some length differences that confuse the model when name similarity is low but non-zero.
- **False Negatives (537):** Primarily occur when addresses are entirely missing or when the strings represent the same entity but are completely lexically distinct (e.g. jaccard=0.0).
